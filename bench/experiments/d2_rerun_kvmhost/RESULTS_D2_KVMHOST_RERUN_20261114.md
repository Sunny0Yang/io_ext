## 1b. 追加实验（2026-11-15）：q_ratelimit 调参对照（cg4，用户要求）

问题：既然 q_ratelimit 的 BPF 语义就是"io.max wbps 镜像"（per-cgroup token bucket，bucket=rate×0.5s），为什么它历史数据远差于 io.max？

调参：**历史 qrl 从未用过正确锚**——bm 旧数据用保守折扣率（k070–074 = 旧锚×0.70–0.74），kvmhost D2 从未配置该臂。本次给它与 io.max 完全同等的待遇：rate_i = 新锚 ref(cg4)×w/Σw = **93/186/280/373 MiB/s**（总和 932 = 实测饱和带），burst 默认 0.5s。

结果（cg4，n=3，全 PASS）：

| iter | 聚合 | JainW | per-tenant 实测 (帽 93/186/280/373) |
|---|---|---|---|
| 1 | 585.1 | 0.913 | **94**（帽✓）/ 163 / 164 / 165 |
| 2 | 522.7 | 0.910 | **85** / 146 / 145 / 146 |
| 3 | 533.5 | 0.908 | **87** / 149 / 149 / 148 |

解释（数据说话）：
1. **限速语义正确**：w1 精确命中 93 帽（±1），token bucket 工作正常；
2. **路径天花板**：q_rl 的 BPF FIFO-hold 派发路径聚合上限 ~530–585 MB/s（none 的 ~70%），w2–w4 帽远未触及却无法更快——这是用户态 hold/派发路径的每请求开销，对照内核 blk-throttle（io.max，779 = none 的 97%）；
3. **饥饿分配非按权**：剩余带宽在未达帽租户间**等分**（163/164/165）而非按帽比例（186/280/373）→ J 停在 0.91。头插 FIFO + token 语义决定了"够帽的租户拿满、不够的均分剩余"，而非按份额比例分摊赤字。

**结论：q_ratelimit 调参后行为正确但有两个结构性上限（路径带宽 ~70%、赤字均分），io.max 的优势 = 内核态 per-request 节流零额外路径开销 + blk-throttle 的比例化配额**。同一负载下若要 1:2:3:4 严格比例且全带宽，静态 io.max 分割仍是饱和 D2 的正解；q_rl 适合"限上限不保比例"的场景。



## 1c. 追加实验（2026-11-15）：bfq+io.weight 正名（用户指出原 bfq 臂未挂权重通道）

原 bfq 臂只切 scheduler=bfq、未配 io.weight → J 0.76（等分），测的不是 bfq 的能力。补跑 `io_bfq_weight` 臂（scheduler=bfq + per-tenant io_bfq_weight=100·w，cg4 无缩放）：

| 采样窗口 | 聚合 MB/s | JainW | per-tenant |
|---|---|---|---|
| 部分损耗窗 #1 | 298 | **0.986** | 36/68/80/114 |
| 部分损耗窗 #2 | 298 | **0.985** | 35/50/93/120 |
| 部分损耗窗 #3/#4 | 394 / 332 | —（逐租户未存档） | |
| 塌缩窗 ×2 | 41–42 | **0.985–0.987** | 5/8/15/14 |
| 混合窗 | 365 | 0.840 | 29/22/145/169（该 iter 疑似 prepare 竞态，权重未生效，待复测） |

**结论：bfq+io.weight 实现按权分配（J 0.93–0.99，典型 0.985，连塌缩窗内都成立），正名成功**；满预算带宽未采到（采样本身消耗读预算，观测区间 298–409，上限估计 ~400–500，与 bfq 自身开销一致；后续在满预算窗补采 iter2 即可）。原 bfq 臂（无权重）数据保留作为"调度器不配权重=等分"的对照。

## 1d. q_ratelimit 弃留判定（速测结论）

5 个干净样本聚合 522–614（最佳 **613.6 @ J 0.913**，98/171/171/171——w1 帽精确命中，其余均分）。判定：**弃用**——
1. 路径天花板 ~613（scx_io BPF FIFO-hold 每请求开销），比 io.max（779）低 21%，与 a_wdrr（621）同级；
2. 赤字均分（J 0.91）而非按帽比例分摊；
3. p99 无优势（部分 iter ~80ms）。
io.max 的内核态优势为定论；q_rl 适合"限上限不保比例"的场景。

## 2. 结论（可直接进论文/报告）

1. **重锚后的 io.max 是该负载形态（全贪心饱和 + 静态权重）的最优解**：每个 cg 都拿到 ~768–780 MB/s（none 的 **95–100%**）同时 JainW 0.97–0.98。旧图"io.max 公平但慢"完全是 320 旧锚的人为产物。机制：share_i = ref(cg)·w/Σw 的静态分割在全贪心场景既按权分配又几乎不损失带宽。**适用边界**：份额是静态的，仅在全贪心饱和下最优；动态负载（D1/dyn_tenant）中工作保持重分配仍有价值。
2. **io_cost（io.weight 通道）实现严格 J=1.000**：cg2–16 全部 9/9 健康 iter 精确 1.000，总带宽恒定 485 MB/s（≈none 的 53–64%，不随 cg 变化）。native、零用户态开销、可复现性达到逐字节级（485.6/484.8/484.7）。
3. **iox 单 arb 族（a_wdrr/a_cost/a_slo）居 Pareto 中段**：cg4/8 健康时 606–622 MB/s @ J 0.90–0.98（none 的 78–80%），**cg16 公平性退化**（J 0.62–0.69，与旧数据一致，是 iox 记账在 16 租户下的已知弱点）；**cg2 有 ~385 MB/s 的固定开销档**（arbiter+BPF 每租户策略路径，与旧 addendum 数据一致）。
4. **none 仍是带宽上限**（888→760），但公平性由构造决定不可用；**bfq 在该平台真实慢**（497→241），且不配 io.weight 时公平性贴等分曲线——挂上 io.weight 后（§1c）J 升至 0.985，属于 native 阵营的第二个人工可用的按权方案。
5. **p99（辅助指标）**：健康 run 量级正常（cg2 ~7–20ms，cg8 ~28–80ms），随 cg 上升；io_max 的硬帽在 cg16 造成队列堆积（p99 ~238ms）；bfq 慢速 run p99 秒级。塌缩 iter 的秒级 p99 已全部打标排除。

## 4. 平台机制（存档）

- 容量型读预算：~40–60GB 全速读后塌缩至 10.2k IOPS（41 MB/s@4k），回补 ~5min；1M 顺序读不受限（IOPS 预算模型自洽）。非 hypervisor drive throttle（宿主截图无 throttle 配置），来自宿主 NVMe 共享层。
- 塌缩窗内所有臂无差异 → canary 前门 + 聚合后门 + 预算内 20s 契约是必要且充分的防线。
- 平台异常史（孤儿 bpftrace、宿主侧限速、回滚）见 `FORENSICS_20261114_platform.md`。
